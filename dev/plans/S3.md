**"SO_REUSEPORT".** USAGE.md:688 says workers > 1 on Windows give no parallelism,
not that they fail, and item 27's premise ("has a test") does not hold: the
tests above run. The 5 single-worker tests marked below pass on a local Windows
Release ZTS build without the line. 6 of 8 multi-worker tests tried the same way
then skip on `exec('curl --version 2>/dev/null')`, which cmd cannot run; 22 test
files check curl that way, so S3.5 replaces the check too.

**What each fix unblocks is not the group count.** 17 HTTP/3 tests need the
aioquic harness, POSIX-only in `_h3_skipif.inc`, so they stay skipped after S3.8.
`h3/001`, `002`, `005` (sockets) and `reactor_pool/008` (hooks) also need HTTP/3;
`websocket/064`-`066` (hooks) then skip on the shared listen fd (#240), and their
SKIPIF prints the first reason without exiting, which is why the log runs two
reasons together. The curl versions are this machine's (System32 8.21, Git 8.11,
neither with HTTP2); the runner's curl is not checked.

**The six of S3.9.** `core/030` uses an AF_UNIX pair only for the stalled peer
(an INET pair does the same); `core/038` and `core/039` test an AF_UNIX listener,
which Windows has (`http_server_class.c:1061`, through named pipes; item 34 is
only the paused case); `core/050` uses SIGKILL only in its teardown;
`multipart/015` uses `/proc/1` and `/dev/full` for its unwritable targets;
`static/025` needs an unreadable file, which an ACL deny gives on Windows.

## S3.5 The 56 "SO_REUSEPORT" skips

Local Windows Release ZTS build (`E:\phpobj-s3`, the S3 configure line: no
HTTP/3, no test hooks, no ext/sockets or ext/openssl), 2026-10-01. The 56 tests
and the three others that checked curl with `2>/dev/null` (`core/039`, `050`,
`054`): 24 pass, 0 fail, 35 skip for a reason of their own group in the table
above (30 HTTP/3, 2 test hooks, 3 POSIX).

Without the line the first run gave 15 passes and 9 failures, all in the tests
themselves: seven pool tests ran `curl ... 2>/dev/null` under cmd, `telemetry/011`
started its curls with `&` and `wait`, and `telemetry/012` found no spread of
connections across workers. `h3/040` and `041` read the core count with `nproc`
and skipped with the wrong reason.

`012` holds 6 to 48 connections over 8 rounds against 3 workers; on Windows one
worker held all of them in 10 of 10 runs. A probe with 30 concurrent requests
(`Async\delay(200)` each) shows the split per worker:

| Workers | Runs | Requests per worker, worker 0 first |
|---|---|---|
| 2 | 5 | 0/30 in all 5 |
| 3 | 20 | 0/0/30 in 13; 0/1/29 and 0/20/10 twice each, 0/5/25, 0/16/14, 0/17/13 |
| 4 | 5 | 0/0/0/30 in all 5 |

Worker 0 accepted nothing in 30 of 30 runs; the worker started last took every
request in 23. `012` treats Windows as it treats macOS: one round, and
`windows-none` when no spread is seen. Whether the pool should spread on Windows
is S3.11. USAGE.md:688 explains the limit with "libuv falls back to a single
accept thread", which the probe contradicts: every worker listens on its own
duplicate of the shared socket (the shared-fd branch in `http_server_class.c`),
and two workers did accept in 7 runs.

## S3.6 ext/sockets, ext/openssl, zstd and the test hooks on Windows

Local Windows Release ZTS build with the CI flags (`/W3 /WX`, plus `/wd4828`
locally: configure writes the Russian OS name into `config.w32.h`), 2026-10-01.
The 54 tests of the four groups: 45 pass, 0 fail, 9 skip, 8 of them for other
groups (4 HTTP/3, 1 curl without HTTP/2, 3 #240 after the hook check). The first
run gave 43 pass and 3 failures:

- `core/020`: `CLICOLOR_FORCE` set with `putenv()` did not reach the sink on
  Windows ZTS (#391), fixed in `http_log.c`.
- `h1/038`: the order of its lines depended on whether the first `write()`
  suspends the handler; on Windows it does and the client printed first. The
  client prints the handler's report after both requests now.
- `h1/055`: skipped on Windows. The test needs the terminator's write parked,
  and on Windows loopback 64 chunks of 64 KiB and the terminator are taken in
  0-1 ms with the peer not reading (3 of 3 runs), so nothing parks.

zstd was never found on Windows: the SDK package names its library
`libzstd_a.lib` (#390). A bare `--with-openssl` builds a shared
