# S3.14 on a Windows machine: measure one AcceptEx against 32

A task for an agent on a Windows machine. It measures; it does not change the
repositories. Report numbers only from runs you made, with the denominators.

## Why

On Windows, php-async (`libuv_reactor.c`, `libuv_listen_start`) calls
`uv_tcp_simultaneous_accepts(handle, 0)` before `uv_listen`, so a TCP listener
keeps one AcceptEx pending instead of libuv's 32. The decision of 2026-11-12
(`dev/DECISIONS.md` in true-async/server) keeps one for a listener that can
pause (a connection cap or CoDel is set) and goes back to 32 for one that never
pauses. Before the code is written we need what each mode costs, with several
workers, and how the accepts split between workers. The only earlier figure is
`dev/BENCHMARKS.md`, 2026-09-30: one worker, 1000 connects take 578-595 ms with
one AcceptEx and 156-172 ms with 32, 7 runs each.

## Builds

Build PHP as the Windows CI job does (`.github/workflows/build-windows.yml` and
`.github/scripts/windows/build_task.bat` in true-async/server): php-src
`true-async` branch, php-async `main`, true-async/server branch
`bug/windows-test-gaps`, Release ZTS, the server linked into php.exe. HTTP/3 is
not needed: leave out `--enable-http3` and `build_h3_deps.bat`.

Make two builds that differ only in php-async:

- **one**: php-async `main` as it is.
- **many**: the same tree with the `uv_tcp_simultaneous_accepts(...)` call in
  `libuv_listen_start` and the error check after it removed, so libuv keeps
  its default.

Record for each build: the three commit hashes, the patch for **many** (a
`git diff`), and `php -v`.

## Server

One PHP script, run by the build under test:

- one TCP listener on 127.0.0.1, backlog 1024;
- `setWorkers(N)` for N = 1, 2, 4;
- the handler answers `ok`;
- `setStatsEnabled(true)` in both configurations;
- after the burst, before `stop()`, the parent reads `$server->getStats()`:
  `['workers']` has one entry per worker, and its `total_requests` is that
  worker's share (one request per connection here). This is how
  `tests/phpt/server/telemetry/012` reads per-worker counters. If a worker
  entry has no `total_requests`, use the per-worker counter that does count
  requests and name it in the report;
- two configurations: **uncapped** (no `setMaxConnections`, CoDel off, the
  defaults) and **capped** (`setMaxConnections(100000)`, a cap that is never
  reached, CoDel off).

The capped run on the **many** build is not a mode the decision will ship; skip
it.

## Load

The 2026-09-30 method, so the numbers compare: 5 client processes of 200
non-blocking connects each for 1000 connects, started at one wall-clock instant
(a start barrier, for example a file they all wait for); each connection sends
`GET / HTTP/1.0\r\nHost: x\r\n\r\n` and reads to EOF. Time is from the first
connect to the last response, measured across the clients. Every response must
be a 200; a run with any other answer or a refused connect is reported, not
dropped. The 2026-09-30 scripts are not in any repository; write the client
and keep it with the report.

## Matrix

7 runs per cell, in the order one, many, one (A/B/A), restarting the server
before each run:

| build | config | workers |
|---|---|---|
| one | uncapped | 1, 2, 4 |
| many | uncapped | 1, 2, 4 |
| one | capped | 1, 2, 4 |

For each run record the time and each worker's `total_requests`. Then repeat one
cell, `one` / uncapped / 1 worker, with 2000 connects (10 clients of 200), 7
runs, to compare with the 2026-09-30 row.

## Report

- Machine: Windows version and build, CPU, logical cores, power plan; whether
  anything else was running.
- The build hashes and the patch.
- A table per cell: min and max of the 7 times, and the per-worker split
  (min-max of each worker's share).
- Whether `one` / uncapped / 1 worker matches the 2026-09-30 range; if not,
  say so and do not adjust anything.
- Anything that failed or looked odd, with the command and its output.
- The server and client scripts, attached.
